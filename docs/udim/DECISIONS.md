## Deviation: Bake Texture node per tile (2026-11-13, branch feat/udim-bake-node-per-tile)
- Resolves the B6 open question "the Bake Texture node repeats its atlas target per tile" (the B6 line above is kept as written). Cause: the bake itself already renders in atlas space into an atlas sized target (bake tool, `tex_coord = input.tex * constants.brush_scale`, no per-tile repeat), but the paint context samples the node's result with `tex_coord`, which repeats per tile with more than one slot. The Bake Texture node now always samples like an image node with `UV: Atlas` (`tex_coord * (1.0 / constants.atlas_stride)`, `parser_material_texture_store`); there is no UV button on the Bake Texture node, its result is always an atlas. Single-slot projects and every other context are unchanged (the atlas expression is only set in the paint context with more than one slot). Like `UV: Atlas` image nodes it follows the fill layer's UV scale and angle (the atlas is scaled/rotated and wraps across tiles); the bake itself also uses the selected layer's (or the header's) UV scale and angle, so the target is a clean atlas only at scale 1 and angle 0 (as before). The material bake export (Materials tab > Bake) also samples the node's atlas once instead of repeating it per tile.
- The Bake Texture node's rasterized bakes (Curvature, Normal, Height, Derivative, Position, TexCoord, Material ID, Object ID, Vertex Color) now paint every tile: the paint shader skips the current layer's tile discard while `bake_texture_node_baking` (set by `bake_to_target`), as for previews and the material bake export. Before, such a bake started with a tile-restricted layer selected left the uncovered tiles black in the result. Raytraced types (Occlusion, Lightmap, Bent Normal, Thickness) already covered every tile (init pass returns before the discard, result copied over the whole target), so the Bake Maps plugin's GPU bake, which also calls `bake_to_target` with raytraced types only, is unchanged. The Bake tool on a layer still respects the layer's tiles.

## Phase B test round 1 fixes (2026-11-13)
- UDIM tiles Auto turns tiles on when the UVs use any tile other than 1001 (several tiles, or a single tile such as 1002) and no triangle crosses a tile border. Before, Auto needed more than one tile, so a mesh entirely in 1002 imported with Auto stayed Off (test 2.7 failed). Off still wraps, On always uses tiles. Supersedes DESIGN.md §2.3 "Auto: On if more than one tile is used".
- Tile list after an import (rule): an import that REPLACES the project's meshes (File > Import > Mesh, File > Reimport Mesh, with or without keeping the layers) sets the tile list to exactly the tiles the new meshes use. An import that ADDS objects (Append, new shapes, appending meshes from a project) keeps the existing tiles and adds the new ones (the list never shrinks there). Before, Reimport Mesh (which keeps the layers) took the append path, so re-importing with UDIM tiles Off left the previous import's tiles in the list as "unused" tiles. With layers kept, the change is a relayout: tiles in both lists keep their pixels, tiles only the previous meshes used are dropped, undo history is cleared ("Tile layout changed" message); going back to the single tile 1001 drops the tile data. With layers cleared it is the fresh path as before (layers resized, 2k per tile for a new multi-tile project).
- Review fixes for the rule above: (a) when the new tiles share no tile with the old list and there are as many (typically 1001 <-> 1002 after Auto changed its decision on Reimport), the tiles are renamed slot by slot instead of relaid out, so the atlas and all paint stay (no history reset). (b) When tiles are dropped, the console names them ("Tiles {tiles} are not used by the imported meshes and were removed with their pixels"). Dropping is still not undoable (relayout clears history). (c) The merged object a relayout builds during the import is removed again so it is rebuilt under the new root. Mesh-only .arm imports start from a new project ({1001}) and replace every object; they keep the append call, which gives the same result there. Not changed: a kept-layers relayout that grows the grid does not apply the 2k-per-tile default of a fresh import (as Append), so a 4096 or 8192 per-tile project grows to large atlases; the clamp warning still applies past 16384.
